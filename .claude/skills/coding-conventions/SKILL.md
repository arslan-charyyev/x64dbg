# Coding Conventions

Conventions for this repository (the in-progress Linux/cross-platform x64dbg port under `src/cross/`). Apply these to any code you write, modify, or review. New conventions will be added over time.

## 1. Consistency with surrounding code

Existing patterns in a codebase reflect decisions, not coincidences. New code should match them by default.

When implementing a feature or fix:
1. **Look at neighboring code first.** How are similar things done elsewhere — file layout, naming, error handling, types, control flow? For this port specifically: how does the nearest already-ported widget wire to the Bridge shim, how does the nearest `ElfBug` `core/process/thread` module handle events, how does `DbgAdapter` translate an ElfBug callback into a Qt signal? Match what you find.
2. **Default to the existing pattern, even if you would do it differently.** Personal preference is not a reason to diverge. Consistency compounds: every reader can predict where to look and how things behave.
3. **If the new requirement genuinely does not fit, do not quietly fork.** Surface the conflict before writing the divergent code:
   - Name the existing pattern and point to where it lives.
   - Name what about the new requirement breaks it.
   - Propose a refactor that updates the existing sites to a new shared shape, so the codebase converges on a single pattern.
   - Ask the user which to do: refactor (preferred) or accept a one-off divergence with a brief comment explaining why.

## 2. Minimal prose in code

Write the least prose the code needs to be understood. Comments and docstrings are liabilities: they drift out of sync with the code, restate what the reader can already see, and bloat the diff. The default is none.

- Don't restate the code. `// increment i` over `i++`, `// read the registers` over `readRegisters()`, a doc-comment that just echoes the function's name and parameters — all noise. Leave it out.
- Prefer names over comments. A clear function, variable, or type name removes the need for the comment that would have explained it.
- Comment only what the code cannot say for itself: a non-obvious *why* (a workaround for a ptrace quirk, an ordering/timing constraint, a deliberate deviation from the obvious approach), a subtle invariant, or a gotcha the next reader would otherwise trip over. If the reason is inferable from the code, leave it out.
- **New fields** on classes/structs get no explanatory comment unless the meaning is genuinely non-obvious from the name and type — no per-field narration.
- This does not override convention 1. When you modify a file whose established style documents every public symbol, match that density — don't strip its comments, and don't bolt narration onto a file that has none. The minimal-prose default governs the new code you write; surgical edits respect the file they land in.

## 3. Repo hard rules (build system, line endings, the Windows/Linux split)

These are specific to how this port reuses the real Windows GUI sources. Violating them breaks either the Windows build or CI.

- **Preserve CRLF in `.cpp`/`.h`.** `.editorconfig` sets `crlf` and `.gitattributes` disables normalization. CMake/`.cmake`/`.toml` are LF. Never convert source line endings to LF.
- **Edit `cmake.toml`, never the generated `CMakeLists.txt`** — they carry a `DO NOT EDIT` banner and are regenerated by cmkr. **The one exception** is `src/cross/widgets/CMakeLists.txt`, which is hand-written and IS where you add ported widget sources (`widgets_SOURCES`).
- **Touching `src/gui/Src/*` affects the Windows build too.** Those files still compile on Windows/MSVC. Guard platform-specific code (`#ifdef`), and **prefer making widgets Bridge-API-driven over sprinkling `#ifdef`** — implement or stub the missing `Dbg*`/`Bridge*`/`Gui*` function in the cross Bridge shim (`src/cross/widgets/Bridge.{h,cpp}`) rather than forking the widget. Don't break the Windows build.
- **Grow the shim, don't grow the ifdefs.** Replacing a Bridge stub with a real implementation (often backed by `ElfBug`, or a real expression evaluator for `DbgEval`) is the expected, normal way to make a widget work cross-platform. Grep `src/cross/widgets/Bridge.cpp` for `TODO`.
- **Formatting is AStyle (Allman), CI-enforced.** Run `uv run --script .github/format/AStyleHelper.py Check` (apply with `Silent`) before proposing any commit that touches C++.
- **Don't auto-install toolchains.** If a build fails on a missing system dependency (a Qt component, `linuxdeploy`), stop and ask — do not pull toolchains.

## Scope

- Applies to anything that would meaningfully diverge: a new pattern, a new style, a new layer of indirection, a new way of doing an already-solved thing.
- Does not apply to trivial additions that fit the existing pattern (a new field, a new case in a switch, an extra parameter that follows the existing shape).
- Not a license to clean up unrelated code while you are there. Stay surgical — propose the refactor, but only execute it if the user accepts.

## Why

Two patterns for the same thing forces every future reader to learn both and every future change to pick one. The cost compounds. The choice is binary: either follow the existing pattern, or update the codebase to a single new one. Do not leave it half-converted. And because this port compiles the *actual* Windows widget sources, a careless `#ifdef` or a forked pattern doesn't just add inconsistency — it can break the Windows build that the same files still serve.
